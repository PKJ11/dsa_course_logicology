# DSA self-paced (kartikvyas.in section)

A standalone Next.js app that will move into kartikvyas.in as the `/dsa` route section. Static export, no server, no AI.

## Run it

```bash
npm install
npm run dev          # http://localhost:3005
npm run build        # static site in out/
```

## Where things live

| Path | What |
|---|---|
| `app/dsa/` | The whole section. Move this folder (plus `public/dsa/`) into the platform. |
| `app/dsa/dsa.css` | The design system, scoped under `.dsa`. |
| `app/dsa/_data/syllabus.ts` | The line: 30 stations, 4 legs. `open: true` marks a written station. |
| `app/dsa/_components/` | Board, route strip, visualizer engine (`Stepper`), array track, course map, practice screen. |
| `app/dsa/_content/<code>/` | One folder per station (pyth, corr, bigo, arrs, bsrc, recr, sort, link, staq, hash, tree, balt, heap, trie, dsuf, rngq, grdy, dvcq, dynp, bits, math, grph, path, span, conn, flow, strg, geom, addp, hard): lessons, figures, problems, tests, solutions. |
| `app/dsa/_content/registry.ts`, `bodies.ts`, `defs.ts`, `solutions.ts` | Station registries read by the route pages and the course map. |
| `public/dsa/runner.mjs` | The Pyodide worker (module worker; Pyodide 314.0.7 from jsDelivr). |
| `public/dsa/harness.py` | Runs learner code against tests, counts reads, switches off tools a problem blocks (`sorted`, `pow`, `heapq` including Python 3.14's `*_max` functions, `bisect`, `itertools.*`, `math.isqrt`, `collections.deque`, `collections.OrderedDict`), runs `expr` tests. Test helpers for linked lists: `chain(values, loop=None, hashable=True)` builds a list (with an optional loop; `hashable=False` makes nodes that cannot go in a set), `walk(head)` lists the values, `nodes(head)` lists the node objects, `place(head, node)` gives a node's position. Trees: `tree(level_list)` builds a binary tree of `TreeNode(value, left, right)` from a level-order list with None gaps, `bst(keys)` inserts keys into a search tree (no recursion), and `levels`, `inorder`, `preorder`, `tnodes`, `height` read a tree back without recursion. Balanced trees (BALT): `unbalanced(root)` lists nodes that break the AVL rule, `rb_check(root)` returns `'ok'` or the first broken red-black rule (nodes have `.red`), `bkeys`, `bcheck(root, most=3)` and `bheight` read and check a B-tree of nodes with `.keys` and `.kids`, `skip_counts(sl)` counts a skip list's nodes per level. `free(x)` returns x and, after the test, empties everything reachable from it, so a big structure the learner built is freed one object at a time. Heaps (HEAP): `counted(values)` wraps numbers in `Num`, which counts every `<`, `<=`, `>`, `>=`; `comparisons()` reads the count and `plain(values)` unwraps. Graphs (GRPH): `is_route(n, edges, p, s, t)` checks a route along two-way edges, `is_cycle(n, edges, c, directed=True)` checks a cycle of different vertices, `teams_check(n, edges, ans)` returns `'two teams'`, `'odd cycle'` or a short note on what is wrong. Weighted graphs (PATH, SPAN): `route_cost(n, edges, p, s, t, directed=True)` gives the total weight of route p along edges `(u, v, w)` (the lightest edge between each pair), or None if p is not a route; `tree_cost(n, edges, chosen)` gives the total weight of chosen edges when they form a spanning tree made from the list (each edge used at most as often as it is listed, either direction), or a short note on what is wrong. Connectivity (CONN): `scc_check(n, edges, labels)` returns `'ok'` when labels number the strongly connected groups 0 .. k − 1 with every edge going to the same or a later group (each group is checked to be strongly connected inside, in O(V + E) without recursion), or a note; `sat_check(n, clauses, ans)` returns `'satisfied'`, `'no assignment'` for None, or the first broken rule (literal k is x_k, −k its opposite). Flow (FLOW): `flow_check(n, edges, flow, s, t)` returns the value of a flow (one whole number per edge `(u, v, c)`) or the first broken rule; `cut_check(n, edges, side, s, t)` returns the capacity of the cut whose source side is `side`, or a note; `match_check(nl, nr, edges, pairs)` returns the number of pairs when they form a matching of allowed edges, or a note. Geometry (GEOM): `crossing_check(segs, ans)` returns `'none'` for None, `'meet'` when ans is a pair of different positions whose pieces share a point (exact whole-number test), or a note. Hard problems (HARD): `cnf_check(n, clauses, ans)` returns `'satisfied'`, `'no assignment'` for None, or the first broken clause (clauses of any length; literal k is variable k, −k its opposite); `oracle_check(find, n, clauses)` runs `find(n, clauses, sat)` with a yes/no helper `sat(formula)` that solves small formulas exactly (DPLL on independent parts, `_cnf_solve`) and counts its calls, and returns `[cnf_check of the answer, at most n + 1 calls?]`; `colour_cnf_report(n, edges, f, planted=None)` checks a formula meant to say "three groups with no edge inside one" (variable 3v + c + 1): small graphs are solved and decoded (`['colouring']` or `['no colouring']`), and with a planted colouring it reports whether the colouring passes, every clash and missing colour is caught, and the formula has at most 4n + 3E clauses; `makespan(jobs, m, a)` returns the busiest machine's total or a note. |
| `scripts/check-problems.py` | Checks every reference solution passes (in a fifth of the time limit) and every naive solution in `scripts/naive/<code>.py` is caught. Run it after editing tests. |
| `scripts/build_<code>.py`, `scripts/tb.py` | Generate `tests/pN.json`: every `expect` is computed from a trusted solution. Run from `scripts/`. |
| `scripts/trusted_<code>.py`, `scripts/cross_<code>.py` | DVCQ, DYNP, BITS, MATH, GRPH, PATH, SPAN, CONN, FLOW, STRG, GEOM, ADDP and HARD keep their trusted solutions in one module, shared by `build_<code>.py` and a brute-force cross-check (`python cross_<code>.py` from `scripts/`: about 3,000 random small cases per problem). Copy this pattern for new stations. `scripts/naive/dynp.py`, `bits.py`, `math.py`, `grph.py`, `path.py`, `span.py`, `conn.py`, `flow.py`, `strg.py`, `geom.py`, `addp.py` and `hard.py` also have an `EXTRA` dict of wrong versions that are run by hand, not by `check-problems.py`. |
| `scripts/sol_<code>.py`, `scripts/solgen.py` | Write a station's `index.ts`, `solutions/index.ts` and `solutions/pN.ts`. |
| `scripts/register.py` | Adds a station to the registries and opens it in the syllabus. |
| `scripts/browser/*.mjs` | Puppeteer checks against the dev server: step every figure (`figcheck`), run references in Pyodide (`pycheck`), run any code on a practice page (`codecheck`; `codecheck2` also prints each failing row's message, such as a stack crash), screenshot a variant (`varshot`), screenshot many variants and steps in one run (`multishot FIG:variant:step:width ...`), find which step of a lesson's figures pushes the page sideways and which elements stick out (`stepover CODE n width`), find overflow (`overflow`), review captures (`capture`), screenshot a lesson section (`secshot`), check every lesson and practice page for sideways scroll at 390px and for code blocks that scroll at 1280px (`pages CODE lessons problems`), run any code on a practice page and print every row with its time (`rows CODE n file.py`), take a finish-review capture set for a session (`capsession <session> <station> ...`: every lesson at 1280 and 390, each figure at two thirds of its steps, the map, and four practice states; it reads `naive_<station>_p<n>.py` beside it for the failing state). `slice.py <dir>` (Pillow) cuts the tall page captures into `slices/` for reviewers. Copy them to a scratch folder with `puppeteer-core` installed. |
| `app/page.tsx` | Stand-in platform home with the DSA card. Not part of the section. |

## Adding a station

1. Create `app/dsa/_content/<code>/` with `meta.ts`, `lesson<n>.tsx`, `algos.ts` and `figures.tsx` (copy any open station). DESIGN.md "Content Folder" describes each file.
2. Write `scripts/build_<code>.py` (tests, with a trusted solution) and run it from `scripts/`. Write `problems.tsx`.
3. Write `scripts/sol_<code>.py` and run it from `scripts/` for the solutions and index files. Write `scripts/naive/<code>.py`: wrong or slow solutions and the tests that must catch them.
4. `python scripts/register.py CODE`, then `python scripts/check-problems.py <code>` and `npx tsc --noEmit`.
5. Linked-list tests: build input with `chain(...)` inside `expr`, and read the answer with `walk(...)`. The harness cuts every link of the nodes `chain` built after each test, because freeing a chain of about 20,000 nodes in one go overflows Pyodide's stack.
6. Tree tests: build input with `tree(...)` or `bst(...)` inside `expr`, and read the answer with `levels(...)` or `inorder(...)`. Nodes built by these helpers have their links cut after each test, like `chain`. Trees the learner builds are not cut, so keep those tests shallow (300 levels at most).
7. Structures the learner builds (an AVL tree, a skip list) are not cut automatically. Wrap them in `free(...)` inside `expr` when they can be large or deep.
8. To test an O(log n) or O(n) bound that a timer cannot see (a C-speed `min()` scan is fast in Python), pass `counted(...)` values and compare `comparisons()` with the bound, as the HEAP tests do. Read `comparisons()` before any other comparison in the expression. `counted()` resets the count, so call it once per test; values added later (an update) are wrapped with `Num(v)`, which counts without resetting (RNGQ-P4). Check the answers against a brute force on plain values inside the same expression (RNGQ-P2).
9. Keep big test answers small: return a summary through `expr` (length, a few values, a check) instead of a 200,000-item `expect`. Do not build data nested more than about 2,000 levels deep; freeing it can crash Pyodide.
10. Size big tests for the laptop at normal speed (a plain `sum(range(30_000_000))` takes about 0.4 s) and leave room: building the test's input inside `args` counts towards the time too. When a faster "naive" exists (a list comprehension instead of a loop), make the list longer and the operations fewer, so O(n) per operation loses clearly to O(log n) or O(√n) (RNGQ-P5, P6). Cross-check a new trusted solution against a brute force on many random small inputs before building tests from it.
11. When many answers are right (any best set of bookings, any optimal prefix code), do not compare with one expected answer. Check the answer in `expr` instead: return a small list of facts such as `[how many, allowed?]` or `[same letters?, prefix-free?, total bits]`, and let the trusted solution fill `expect` (GRDY-P3, GRDY-P5). Pass the learner a copy (`list(b)`, `dict(c)`) and check against the original, so sorting the input in place cannot change what is checked.
12. A bound that grows with n can be checked by counting at two sizes. DVCQ-P6 counts comparisons on 2,000 and 64,000 values and allows at most 25% more per value on the longer list: a linear method stays flat (about 7.7 and 8.2), while sorting a copy grows by about half (log₂ n per value). Add a fixed cap too (20n there), and inputs built against simple rules (a sorted list, all-equal values, a list built so the middle value is always the smallest left).
13. Recursion depth in the browser is smaller than in CPython. Plain Python recursion and a memo kept in a dict go past 1,000 nested calls in Pyodide, but a function wrapped in `functools.cache` (a C wrapper) overflows the browser's stack at about 250 nested calls, shown as "Python itself stopped (Maximum call stack size exceeded)". When a problem says memoised recursion is fine, keep its depth under 200 (DYNP-P1 goes to n = 200). When big tests are meant to defeat memoised recursion, say "fails", not "fails with a RecursionError": in the browser it may be a stack crash instead.
14. Randomised code must be tested without luck. Pass the random function in as an argument and let each test supply fixed answers (MATH-P7's `rand(m)`). Make scripted answers respect the range the code asks for (`next(it) % m`), or an off-by-one call such as `rand(i)` instead of `rand(i + 1)` still gets in-range answers and passes. To check fairness exactly, try every run of answers with `itertools.product` inside `expr` and count the outcomes: each must come out equally often. Check the arguments of the calls too, in one test that records them.
15. Pseudo-random inputs built in `args` must be well spread. A formula like `(k * k * 7919 + k * 104729) % (2 * 10 ** 12)` stays far below the modulus for small k, so every value came out near the bottom of the range and the empty choice was the best answer (BITS-P5's first draft). Use a 64-bit multiplier, `(k * 6364136223846793005 + seed) % 2 ** 64 % mod`, and look at the expected answers before trusting a test: an answer of 0, or equal to the target, often means the data is weak.
16. Pseudo-random numbers made by one multiplication (rule 15) are evenly spread as one list, but each value is the last plus a fixed step, so two of them made from the same k are linked and a grid made from them shows stripes (GRPH's first mazes were striped and unreachable, and the "random" questions of GRPH-P1 repeated real edges). For graphs and grids, mix the bits: `for y in [(k + seed) * A % 2 ** 64] for x in [(y ^ y >> 29) * B % 2 ** 64]` inside the comprehension, then read different bits for different numbers, `(x >> 8) % n` and `(x >> 36) % n` (`mix()` in `build_grph.py`). Use seeds far apart (`seed * 10_000_019`), or two seeds give the same numbers shifted by a few places. Do the mixing inline, not through a lambda per number: building the input counts towards the test's time, and a lambda call per number made GRPH's big tests twice as slow.
17. Time a slow method in the browser before trusting it to fail. `list.pop(0)` on a list of 200,000 items is about 25 times faster in Pyodide in Chrome than in CPython on Windows (the move fits in the processor's cache), so a BFS with a list as its queue passed GRPH-P2's 200,000-item test in the browser (1.5 s) while CPython took 39 s. `check-problems.py` only runs CPython; check such naive versions with `rows.mjs` too. The test now has 500,000 items (about 10 s in the browser).
18. Build big inputs whose answer is known by construction when the trusted check is itself the problem (PATH-P1): plant the answer (a rising distance for each rank of a scrambled order, one tight edge into each rank from an earlier one, extra edges that never make anything shorter). Make planted structures deep and list them against the order a naive method would follow (edges from the far end), or a method that repeats rounds until nothing changes finishes in a few rounds and passes (PATH-P1, P5). Equal values sort faster: a test full of ties may not defeat a sort-everything method that a random test does (SPAN-P3).
19. When a test is meant to need a faster method for the same problem (Dinic over Edmonds-Karp, Hopcroft-Karp over one search per free vertex), time both on the *actual* test input, not on a similar one made with Python's `random`: FLOW's first layered network and matching test separated the methods by 5 s against 0.3 s with `random`, but by only 3.6 s against 0.2 s when built with `mix()`, which a 4-second limit does not catch in CPython. Make the gap at least five times the limit in CPython, then confirm in the browser with `rows.mjs`. Also time the input building: a 4,800-vertex layered network took 0.33 s to build, so its test got 5 seconds. A naive method that happens to search in a lucky order can pass a trap built for another order (FLOW-P2's greedy paths): no small network fooled list-order DFS, BFS and stack order at once, so give each common order its own trap.
20. Slices, `in`, `find` and hashing a slice all run in C, so a method that is O(n · L) in letters can still pass. STRG-P4's binary search with a set of slices passed `'ab' * 25000` (the answer is near n, so each length tried has few pieces); it fails only when every length tried is near n/2, with about n/2 pieces of n/2 letters each, so the test is a random half written twice, at 100,000 letters (34 s against 0.37 s for the rolling hash). A naive version that copies every suffix (`key=lambda i: s[i:]`) needs n²/2 letters of memory: in the browser it fails with a MemoryError row, but in CPython it would fill the laptop's memory, so `scripts/naive/strg.py` uses a comparison-based sort for `check-problems.py`, and the copying version is run only in the browser with `rows.mjs`.
21. Run every `EXTRA` wrong version against the final tests, and make sure the input is one where its mistake matters. Two slipped through D5's first test sets for different reasons. HARD-P4's "scan every machine with `min(load)`" is O(n · m), but `min()` runs in C (rule 20 again): 200,000 jobs on 1,000 machines took under 4 seconds, so the big test now has 10,000 machines. ADDP-P6's "look back only 100 stations" gave right answers because the test's best runs were short (groups of 50 stations); dense stations with expensive stops, whose best runs span over 10,000 stations, catch it. Also check that each claimed trap really is one: "Two loops joined" was meant to catch a search that never revisits a junction, and it did not.
